# KNOWN_LIMITATIONS (Song Critic Sequential V1)

1. **Two songs, two backends, one run each, no retry:** 4 comparable cells. The result is an indication, not a statistic. Both songs were already known to the auditor from earlier audits (neutral titles do not hide that).
2. **Quality judgment is one reader's** reading of the raw answers; the mechanical checks (quote/line verification, tokens, latency) are scripted and the same for both arms. No LLM judge.
3. **One prototype only:** one short system prompt, one set of nine step prompts. A different wording of the steps (for example asking each step to find the best argument against its own `strength`) was not tried by design (no tuning after seeing results), so this test cannot say that sequential analysis can never work, only that THIS prototype does not beat the one-shot.
4. **Step prompts carry the same reading tools as the earlier V3 candidate** ("repetition can be deliberate", "stillness is not proof of failure"). They may have been read as permissions. Not isolated.
5. **Session types differ by backend:** Gemma = real server-side session (one id per song); Grok = stateless API with the full history replayed by the client. Neither is a summarized "state carry". Gemma used about 62 % of the context by the app's own (cautious) estimate; a longer song might stop at the guard, which is by design: it never opens a second session.
6. **Grok S3 Step 9 is incomplete** (ends inside `[NOTE.1]`, no `[DONE]`; the finish reason was not captured by the prototype's request wrapper). It was not retried. The Action Plan and the recall fields are present. It counts as a format failure for B.
7. **Gemma leaks the end token `<end_turn>`** after `[DONE]` (8 of 22 Gemma answers end with `[DONE]<end_turn>`; in some answers it is attached to the last line). The first run of the checker treated that as part of the last quote and reported 7 and 1 false "unverified" quotes; the checker was fixed to treat a line starting with `[DONE]` as the end. This fix was made after seeing the result but concerns only the verifier, not the prompts or the models; the raw answers are unchanged. Numbers in this report are with the fixed checker.
8. **Tokens:** Gemma reports none (estimates only); Grok's are the API's. The Grok wrapper in `run_seq.py` copies the request body of `llm_chat.ask_grok` (same URL, model, temperature 0.4, `reasoning_effort: low`, `max_tokens` 4096) in order to read the usage; arm A on Grok used the same wrapper (not `ask_grok` itself) so both arms are measured alike.
9. **Production untouched:** no change to the production prompt, parser, UI, model settings or the llm_chat helpers; no commit; no audio; no other specialist called. The files written are in `docs/song_critic_sequential_v1/`, with one exception (item 10).
10. The Gemma calls went through `LC.ask_local`, which appends a line per call to `%LOCALAPPDATA%\WorkflowPad\logs\ai_calls.log` (an existing logging behavior of the helper, not settings). That is the only write outside the docs folder, and it is a deviation from "do not touch AppData" in the brief (20 appended log lines: 2 one-shot + 18 step calls to Gemma); the runner did not pass through any other AppData file. No setting was changed.
11. Evidence checking looks only at `lines` + `quote`; whether a claim in the reasoning is true of the lyrics was read by a person for the 8 final reports and the step conclusions, not for every sentence of the 36 step answers.
